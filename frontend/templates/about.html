Core Architectural Highlights

Preventing double bookings is a classic distributed systems problem. Two reservations $[A_{start}, A_{end}]$ and $[B_{start}, B_{end}]$ for the same bike conflict if and only if: existing.start_time < requested.end_time AND existing.end_time > requested.start_time In booking_service.py, we validate availability inside an atomic database transaction before persisting the record, ensuring strict consistency.

Hard-deleting records in production breaks historical booking tables, foreign key integrity, and revenue auditing. Our system implements soft-deletion via an is_active boolean flag. If a bike has historical bookings, deleting it in the admin console marks it inactive rather than destroying historical invoices.

Customers are strictly prevented from viewing or cancelling bookings belonging to other users. Every reservation query and state-changing action checks: if booking.user_id != current_user.id and not current_user.is_admin: abort(403) Administrative routes are locked down using a custom Python decorator @admin_required.

All state-modifying POST requests (logins, registrations, reservations, cancellations, and bike updates) carry a cryptographic synchronizer token verified by Flask-WTF CSRFProtect. Database queries are exclusively executed through SQLAlchemy's parameterized queries, neutralizing SQL Injection.
